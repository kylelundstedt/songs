# Metadata population plan

## Recommendation

Populate metadata with a deterministic harvester first, then use a small number of cheap-model subagents only to adjudicate matches. Do not ask hundreds of agents to search the web independently.

Use **five `gpt-5.6-luna` subagents**:

- four batch reviewers, each responsible for about 71 songs (processed in smaller 20–25 song packets);
- one independent QA reviewer over the combined proposals.

A single coordinator/script should make all provider requests sequentially, cache responses, score candidates, and write proposal files. This avoids duplicate requests, inconsistent source selection, provider throttling, and merge conflicts. Escalate only the small unresolved queue to a stronger model or a human.

## Current catalog baseline

- 284 canonical Markdown songs.
- The canonical songs currently have no YAML metadata.
- 293 Notion migration candidates are available as a second source of band-arrangement evidence.
- A preliminary conservative title normalization matches 233 canonical songs to Notion candidates.
- 86 of those strict matches have an apparent key token in the Notion title. Treat these as candidate **performance keys**, not original-recording keys.
- The current app already supports LRCLIB and Lyrics.ovh recording/lyrics lookup, with Deezer lookup for original BPM.

These counts should be regenerated by the enrichment script and committed as a machine-readable baseline rather than treated as permanent constants.

## Important metadata distinctions

Keep these concepts separate:

1. **Canonical song** — the song represented by the lead sheet.
2. **Reference recording** — a specific artist/release/recording used to identify artist, duration, album, and original-recording metadata.
3. **Band arrangement** — the key and tempo actually performed by the band.
4. **Lyrics provenance** — where the words in the canonical Markdown actually came from.
5. **Lyrics reference** — an external provider record whose lyrics strongly match the canonical sheet.

For the 284 migrated files, an LRCLIB match is a useful external reference, but LRCLIB did not supply the existing text. Therefore, do not label LRCLIB as the lyrics `source_provider` for an existing file. Preserve the legacy Git migration as its provenance and store LRCLIB separately as a reference recording/lyrics match.

Suggested fields, subject to the app-design session's schema decision:

```yaml
artist: "Billy Idol"
performance_key: "E"
bpm: "128"

reference_title: "Rebel Yell"
reference_artist: "Billy Idol"
reference_album: "Rebel Yell"
reference_duration_seconds: 285
recording_mbid: "..."

original_key: "Bm"
original_key_kind: "analysis-estimate"
original_bpm: "166.04"

provenance_status: "legacy-imported"
legacy_source_commit: "6cfbda8e..."
legacy_source_path: "lead-sheet/Rebel-Yell.md"

lyrics_reference_provider: "LRCLIB"
lyrics_reference_id: "12345"
lyrics_reference_url: "..."
metadata_review_status: "auto-approved"
metadata_confidence: 0.97
```

`original_key_kind` should distinguish a published value from an audio-analysis estimate. Unknown values should remain absent rather than guessed.

## Source strategy

### Artist and recording identity

Use this order:

1. Existing canonical title and any arrangement/version qualifier.
2. Notion candidate title and content as band-specific evidence.
3. LRCLIB candidates for title, artist, album, duration, provider ID, and a lyrics fingerprint.
4. MusicBrainz for durable artist/recording/release IDs and recording identity.
5. Lyrics.ovh/Deezer as a fallback recording search and BPM source.

MusicBrainz should be an identity authority, not a key/BPM source. Keep one central rate-limited client with a meaningful User-Agent.

### Lyrics reference matching

Use the existing lyrics to improve candidate selection, but do it deterministically:

1. Strip Markdown headings, measure counts, stage cues, punctuation, and repeated-section abbreviations from the canonical body.
2. Fetch candidate lyrics transiently from LRCLIB.
3. Compare normalized token shingles and ordered-line similarity.
4. Store only provider IDs, response hashes, scores, and retrieval metadata in the proposal cache—not duplicate full lyrics.
5. Auto-accept only when title/artist evidence and lyric similarity agree.

This can identify the likely artist/recording far more reliably than title-only matching, especially for songs with common titles. It will be weaker for heavily abbreviated lead sheets and should send those songs to review.

### Performance key

The Notion title suffix is the best existing source for the band's key. Extract it as a proposal only when:

- the Notion/canonical title match is unambiguous;
- the suffix parses as a valid key;
- it is not part of the actual song title or a medley/version note.

Require review before committing. Never overwrite an explicit canonical performance key in future reruns.

### Performance BPM

Do not copy original BPM into `bpm` automatically. The band's tempo may differ. Populate performance BPM only from explicit band material or human confirmation. The app can make later review fast by showing original BPM as the suggested starting value.

### Original BPM

Use Deezer where the selected recording matches confidently. Preserve the provider track ID and retrieval timestamp. If a second source disagrees materially, queue the value for review rather than averaging it.

### Original key

LRCLIB, MusicBrainz, and the existing Deezer adapter do not establish original key. Recommended options:

1. Query the historical AcousticBrainz archive by MusicBrainz recording ID where data exists; save the result as an **analysis estimate** with its algorithm/source.
2. If the user later supplies legally available audio files, analyze them locally with Essentia/KeyFinder and retain confidence/algorithm details.
3. Otherwise leave `original_key` blank and add it through the review UI.

Do not scrape consumer sites such as Tunebat or Musicstax. Do not use an LLM to guess key from lyrics, artist, or title.

## Pipeline

### Phase 1: schema and inventory

Create a deterministic command such as:

```text
songs-metadata inventory
songs-metadata harvest
songs-metadata review-batches
songs-metadata apply
songs-metadata verify
```

The inventory output should contain one row per canonical file with body hash, normalized title, detected qualifiers, Notion candidates, and current metadata. It must fail on duplicate IDs or unexpected body changes.

### Phase 2: centralized harvest

One process:

- searches providers sequentially and honors retry/rate-limit responses;
- caches raw JSON outside canonical song files;
- records request URL/parameters, provider IDs, retrieval time, and response hash;
- computes candidate scores;
- emits a compact proposal JSON per song.

Suggested confidence rules:

- **Tier A / auto-apply:** strong title and artist agreement, no version conflict, and strong lyrics similarity; BPM tied to the same recording.
- **Tier B / subagent review:** strong title but ambiguous artist, album, live/single/remix status, duration, or moderate lyric similarity.
- **Tier C / human review:** common-title collision, medley, live/custom arrangement, conflicting providers, sparse lyrics, or materially different lyric text.

Begin with a 20-song pilot spanning obvious, ambiguous, live, medley, and common-title cases. Tune scoring thresholds before harvesting all 284.

### Phase 3: four Luna reviewers

Give each reviewer only compact proposal packets, not the full repository. Each packet should include:

- canonical title and relevant qualifiers;
- short non-copyright lyric fingerprints or selected matching snippets kept within safe limits;
- Notion title/key evidence;
- ranked provider candidates and deterministic scores;
- explicit allowed decisions: accept candidate, reject candidate, or escalate.

Reviewers write structured JSON decisions and never edit song Markdown directly. Reuse the same four agents for successive 20–25 song packets so instructions and judgment remain consistent.

### Phase 4: independent QA agent

The fifth Luna agent checks:

- artist/recording consistency;
- suspicious original/performance key equality;
- suspicious original/performance BPM copying;
- live, acoustic, remix, cover, and medley mismatches;
- low-confidence auto-accepts;
- provenance/reference misuse;
- duplicate recording IDs assigned to unrelated songs.

A stronger model is warranted only for the final ambiguous queue, likely tens of songs rather than the full catalog.

### Phase 5: apply and verify

The deterministic apply step should:

- modify YAML front matter only;
- prove the Markdown body hash is unchanged;
- preserve existing explicit metadata;
- generate one review report with accepted, unresolved, and rejected candidates;
- render all 284 songs with Apex;
- run Go tests and catalog validation;
- commit changes in reviewable batches, not one opaque 284-file commit.

Recommended commits:

1. schema, inventory, cache format, and pilot fixtures;
2. Tier A artist/reference metadata;
3. reviewed performance keys from Notion;
4. original BPM and optional key estimates;
5. manual corrections and unresolved-queue report.

## Expected result

The first pass should aim for high-confidence artist and recording-reference coverage, not artificial 100% completeness. A blank original key is better than a confidently presented wrong key. The likely order of attainable coverage is:

1. artist;
2. lyrics/reference recording link;
3. original BPM;
4. performance key from Notion;
5. original key estimate;
6. human-confirmed performance BPM.

This approach keeps provider access auditable, limits model cost, preserves the existing lead sheets, and makes reruns deterministic when providers or the catalog change.
